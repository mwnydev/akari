# 论坛 + USDT 担保交易 开发计划 v3（Rust · Arbitrum）

Oct 17, 2026 · @lam

后端 Rust，合约 Solidity，前端 TypeScript + Next.js（App Router）+ Tailwind CSS；只上 Arbitrum One 一条链。所有依赖采用 2026 年 10 月的最新稳定版。预计第 22 周上线，第 24–26 周开放拍卖。

## 1. 项目概述与原则

建一个内置去中心化 USDT 担保交易的论坛：普通用户用邮箱注册即可使用论坛，只有需要交易时才开通 Passkey（Face ID / 指纹）和 AA 智能钱包，无需助记词、无需持有 ETH。

**设计容量（理论暂定，用于压测和容量规划，不是上线指标）**：2 万注册、2000–3000 同时在线、2000 万帖子。实际按增长调整，扩容按第 13 节的触发条件执行。

**范围**

- 完整论坛：账号、板块、主题与楼层、私信、通知、搜索、内容管理（发帖免审核）、后台、帮助中心
- 担保交易：链上合约托管 USDT，一次性放款和分期放款两种模式，超时自动处理，争议由平台仲裁员裁决
- 钱包：按需开通的 ERC-4337 智能账户；Arbitrum One 的 gas 只能用 ETH 付，全部由平台自有 Paymaster 用 ETH 代付，用户钱包永远不需要 ETH；平台再以 USDT 收回（付款前的操作收代付费，付款后的操作在结算时扣固定 gas 费），平台不为 gas 倒贴
- 运营：站长、超级管理员、管理员、版主、仲裁员分权；金库、运营钱包、薪资钱包分开管理
- Telegram：通知机器人、官方频道、仅论坛用户可入的群聊

**最高原则**

1. **性能和安全优先**于功能数量和上线日期；达不到第 12 节指标或没过安全关卡就不上线
2. **资金只在链上**：用户托管资金只有合约规则能动，平台、站长、管理员都转不走
3. **不图增障碍**：门槛只放在动钱和改权限这两类操作上，其他操作尽量一步完成
4. **用户不在钱包长期存钱**：每笔交易都是「交易所提币 → 担保 → 提回交易所」，所以选交易所提币费低、gas 便宜的 Arbitrum One

**关键决策一览**

| 项目 | 决定 |
| --- | --- |

## 2. 系统架构

后端是四个 Rust 程序（api、worker、indexer、sponsor），共用一个 Cargo workspace；钱包签名在浏览器完成，经 forum-api 转给 forum-sponsor 签字并直接提交上链（第三方密钥不下发到浏览器），后端只从链上读取结果，indexer 是链上状态进入论坛数据库的唯一入口。

&#91;embedded content: 系统架构 · 单机服务 + 链上合约\]

所有运行我们自己代码的部分都在自有服务器上；放在外部的，要么是安全上必须隔离，要么是自有服务器做不了或做不好。

| 组件 | 位置 | 原因 |
| --- | --- | --- |
| 论坛页面、API、worker、indexer、数据库、缓存、监控 | 自有服务器 | — |
| 钱包与后台页面 | Cloudflare Pages | 服务器被攻破也改不了用户签名时看到的页面 |
| CDN、WAF、防 DDoS | Cloudflare | 攻击流量必须在到达服务器前挡住 |
| 图片与数据库备份 | Cloudflare R2 | 备份不能和服务器放在一起；图片流量不占服务器带宽 |
| 合约、USDT、Safe | 区块链 | 担保的前提就是资金不在任何人的服务器上 |
| RPC 节点；故障备用的第三方 Bundler（平时由自写私有代发器提交，见第 5 节） | 第三方 API（每类至少两家） | 自建节点需要远超本服务器的配置；备用 Bundler 平时不产生费用 |
| 邮件发送 | Resend 与 SMTP 服务商 | 自建发信容易进垃圾箱 |

**架构要点**

- **事务发件箱**：业务数据和「待发送通知」同一事务写入，worker 再发送（站内、WebSocket、Telegram、邮件）
- **关键任务放数据库**：发薪、超时处理、通知用 apalis（PostgreSQL 队列）；Valkey 只放可丢的缓存和推送，并开 AOF
- **链上状态分级确认**：界面、站内与 Telegram 通知、后续操作代付校验按最新区块（latest）即时响应；数字商品自动发卡密等最新区块后数个块（或 safe 标记）；财务记账、信誉统计、经验与薪资只认最终确认（finalized，Arbitrum 约晚 15–20 分钟）的区块
- **数据库分账号**：只有 indexer 能写订单和链上事件等派生表
- **图片直传 R2**，worker 异步转 WebP；**后台独立前端**，和钱包一样放 Cloudflare Pages
- **链路追踪**：api、worker、indexer、sponsor 接入 OpenTelemetry
- 刻意不做：微服务拆分、Kubernetes、Kafka——按本项目规模只增加运维负担
- **indexer 省调用**：用 RPC 的 WebSocket 订阅合约事件即时显示，每 20 秒按区块范围批量补拉校对（`INDEXER_RECONCILE_MS` 可调；5 秒时单 indexer 一天约 700 万 Infura credits，超出免费档），不逐块轮询（Arbitrum 约 0.25 秒出一个块，逐块轮询会让 RPC 账单翻几倍）
- **浏览器不直连第三方**：钱包页提交操作、读链上状态都经 forum-api 代理；代理只转发本站钱包的操作并限流，读链结果走 Valkey 缓存，RPC 与备用 Bundler 密钥只在服务器

**现成中间件（能用现成的就不自己写）**

| 环节 | 采用 | 说明 |
| --- | --- | --- |
| HTTP 服务与中间件 | axum + tower-http | 压缩、超时、CORS、请求追踪都是现成中间件 |
| 会话 / 签名 Cookie | tower-sessions（Valkey 存储）+ axum-extra SignedCookieJar | 会话 Cookie 带 HMAC 签名，伪造的直接当游客 |
| 限流 | tower\_governor（单进程兜底）+ Valkey 滑动窗口 | Rust 生态没有成熟的跨进程限流库，只自写这几十行 |
| 任务队列 | apalis + apalis-postgres | 任务存 PostgreSQL，和业务数据同库，经发件箱入队 |
| OpenAPI | utoipa | 由 Rust 类型生成接口文档，前端再生成 TypeScript 客户端 |
| Passkey | webauthn-rs | 服务端验证注册与登录 |
| 链上读写 | alloy | 合约绑定、事件订阅、发交易 |
| 智能账户 / Paymaster | ZeroDev Kernel / Pimlico singleton-paymaster（开源经审计），两者锁定同一个 EntryPoint 版本 | 不自写账户和 Paymaster |
| 交易提交 | 自写私有代发器（alloy，约数百行） | 只提交本站用户的操作，比部署 Rundler、Alto 这类公共 Bundler 简单，也不需要付费追踪 RPC；第三方 Bundler 只作故障备用 |
| 链上事件索引 | 自写 indexer（alloy） | 评估过 rindexer（Rust，配置即可写入 PostgreSQL），但文档没写区块回滚处理；我们需要回滚撤销与最终确认分级，单链、合约少，自写更可控 |
| 邮件 / Telegram / 图片 / HTML 过滤 | lettre + resend-rs / teloxide / libvips / ammonia | 均为各领域主流 crate |

## 3. 技术栈与版本

全部采用 2026 年 10 月 15 日查到的最新稳定版（npm、crates.io、Rust 官方发布渠道、各项目官方发布页），开工时锁定精确版本，之后由 Renovate 每周自动提依赖升级 PR，CI 全绿才合并。

**版本策略**

- 一律用最新**稳定版**，不用 beta / RC；数据库这类核心组件出新大版本后，等到第二个小版本（x.2）再升级
- 所有版本在 `Cargo.lock`、`rust-toolchain.toml`、`pnpm-lock.yaml`、`foundry.toml` 和部署脚本里锁定精确版本，任何环境装出来都一样
- 安全补丁 48 小时内升级；功能性升级跟随每周的 Renovate PR
- 本表是开工时的基线，开工当天用同样方法再核对一次

## 5. 账号、Passkey 与钱包

只逛论坛的用户不需要 Passkey 和钱包；第一次要交易时才开通，普通用户只有这一个钱包 Passkey（论坛登录用邮箱验证码，不设登录 Passkey，密码管理器里只有一条记录，不会搞混或删错），只在钱包子域名使用。钱包逻辑全部在浏览器端完成，后端从不接触用户私钥。

**注册与登录**

| 用户类型 | 登录方式 | 能做什么 |
| --- | --- | --- |
| 普通用户 | 邮箱验证码（无密码，10 分钟有效、限次 + Turnstile）；登录保持 30 天；新设备登录发邮件通知；不设登录 Passkey | 论坛全部功能，不能交易 |
| 已开通交易 | 邮箱验证码（与普通用户相同）；钱包 Passkey 只用于确认资金和敏感操作 | 只凭邮箱登录不能做任何资金或敏感操作 |
| 管理人员 | 只能 Passkey | 见第 9 节 |

会话：HttpOnly + Secure + SameSite=Lax Cookie（Strict 会让从邮件、Telegram 点进来的用户显示未登录；写操作另有 Origin 校验防 CSRF），存 Valkey，登录后轮换，闲置 30 天过期，可在设置里踢出其他设备。后台 Passkey 登录检查 sign\_count 时，对同步型 Passkey 固定返回 0 的情况放行。

**开通交易（首次发交易帖、点担保购买、领取薪资或报酬时触发，也可在设置里主动开通）**

1. 后端生成一次性 challenge（存 Valkey，5 分钟过期）→ 在钱包子域名页面创建钱包 Passkey，RP ID = 钱包中心域名（不是论坛主域名，见下文「Passkey 中心域名与关联域名」）；Passkey 显示名称固定为「品牌名 钱包签名（勿删）· 用户名」，在密码管理器里一眼可辨
2. 后端用 webauthn-rs 验证，保存 credential\_id 和公钥
3. 前端用同一公钥通过 ZeroDev 计算智能账户地址（不上链，初始参数固定，保证 CREATE2 地址永不改变），写入 wallets 表；钱包在第一次链上操作时顺带部署，部署的 `initCode` 初始化调用中默认给平台 Paymaster 合约授予 USDT 额度（验证阶段完成，不随业务 `callData` 回滚）
4. （P1，ADR 0007）生成恢复码：第一单不打断，订单完成后提示保存；第二单开始前必须保存（离线恢复包同时包含恢复码与账户 `initCode` 派生参数，确保从未发过链上交易但已收款的卖家钱包也能在链外先部署再恢复）。上线时先引导绑定第二台设备的 Passkey

开通前用户只看到「开通交易」入口，看不到任何钱包界面。

**恢复与账号安全**

- iCloud 钥匙串、Google 密码管理器的 Passkey 自动同步，换手机不丢；可再绑第二台设备的 Passkey（钱包未部署前先在服务端登记，首次链上部署时一并写入智能账户签名者列表，避免改变初始地址；已部署则发一笔链上交易添加）；钱包页检测到 Passkey 不见了（如被误删）时直接引导到第二设备或恢复码流程；帮助中心用图说明这条记录不能删
- **恢复码（P1，ADR 0007）**：离线保存，作为钱包的恢复人，不依赖域名。它不能直接转账，只能发起「更换签名者」，48 小时后生效，期间原 Passkey 可一键取消；生效后可在任何钱包工具里取回资金（脱离论坛时没有平台代付，需自行往钱包转少量 ETH 作 gas；若钱包尚未部署，恢复工具用保存的 `initCode` 一并部署）
- **域名是单点**：Passkey 绑定中心域名，域名丢失将无法签名。对策：可靠注册商 + 注册商锁 + 双重验证，加上恢复码兜底
- **敏感操作必须 Passkey 确认**：新增或修改提币地址、提回交易所、私信发起担保、修改邮箱、绑定或移除 Passkey、修改恢复码（未开通钱包的用户改邮箱用旧邮箱验证码）。邮箱被盗的人能登进论坛发帖聊天，但发不出担保报价、改不了地址和邮箱、动不了钱
- **提币地址冷却**：第一个地址立即可用；之后新增或修改的地址 24 小时后生效，期间可撤销（这是界面层保护，防的是会话被盗后偷换已保存的地址；真正动钱仍需钱包 Passkey）
- 新设备、新地区登录时站内 + 邮件提醒
- **钱包 Passkey 只认钱包域名**：智能账户在链上只校验签名内容，不校验发起签名的网页。如果钱包 Passkey 的 RP ID 是论坛主域名，被入侵的论坛服务器或一处 XSS 就能把「请求登录」伪装成签名一笔转账，用户刷一次 Face ID 就被盗。钱包 Passkey 绑定钱包中心域名后，论坛主站在浏览器层面就无法请求它
- **恢复码在钱包页面本地生成**，服务器只收到对应的恢复地址；更换签名者的 48 小时延迟期间，站内、邮件、Telegram 三路提醒
- **已验证（ADR 0005）**：ZeroDev 官方恢复模块没有延迟；P1 自写最小的延迟恢复模块，上线时不部署

**Passkey 中心域名与关联域名**

用 WebAuthn 的「关联来源请求」（Related Origin Requests）：Passkey 只绑一个中心域名，其他域名在中心域名的 `/.well-known/webauthn` 文件里登记后也能使用同一个 Passkey。加备用域名、换入口域名时，用户的 Passkey 和钱包地址都不变。

| 分组 | 中心域名（RP ID） | 可登记的关联域名 |
| --- | --- | --- |
| 后台登录 | 后台中心域名 | 只有后台域名 |
| 钱包签名 | 钱包中心域名 | 只有各域名下的钱包子域名，绝不包含任何论坛主站 |

- **两组互不相通**：论坛主站的 XSS 既请求不到钱包签名，也请求不到管理员的后台登录凭证
- **关联文件不放自有服务器**：两个中心域名的 `/.well-known/webauthn` 都部署在 Cloudflare Pages，由 CI 签名发布；服务器被攻破也加不进恶意域名。修改域名列表走代码审查 + 人工批准的发布流程，不在后台在线改
- **浏览器支持**：Chrome / Edge 128 起、Safari 18 起已支持，Firefox 正在实现（开工时实测）；不支持的浏览器自动跳到中心域名完成签名再跳回
- **数量限制**：浏览器按「不同主域名」计数，至少支持 5 个，按每组最多 5 个主域名规划
- **中心域名是单点**：选最稳的主域名当中心，不用备用域名；注册商锁 + 双重验证 + 恢复码兜底。链上钱包只认 Passkey 公钥，增减关联域名不影响资金

**AA 智能钱包**

| 环节 | 做法 |
| --- | --- |
| 账户 | ZeroDev Kernel + Passkey 验证器，部署在 Arbitrum One |
| 交易提交 / Paymaster | Paymaster 自有（开源且经审计的合约），平台用 ETH 统一代付；交易由后端自写的私有代发器直接调用 EntryPoint 提交；第三方 Bundler（如 Pimlico）只作故障备用，切换只改配置 |
| 批量交易 | 下单时 `approve` + `createAndFund` 合成一次 Face ID（首次上链时 `initCode` 已含对 Paymaster 的默认授权） |
| 充值 | 显示地址、二维码和当前网络图标；醒目提示交易所提币须选 Arbitrum One 网络，选 TRC20 无法找回 |
| 提回交易所 | 粘贴交易所充值地址（可保存），明文显示金额、地址前后 6 位和网络；代付费（USDT）从提出金额中扣，「全部提回」自动算好 |

**gas 规则（平台不为 gas 倒贴）**

- **全部由平台代付 ETH，不用第三方代付服务**：Arbitrum One 的 gas 只能用 ETH 支付，但用户钱包永远不需要 ETH。自有 Paymaster 合约在 EntryPoint 里存 ETH 押金替用户付 gas，省掉代付服务商 10–20% 的加价；交易由后端私有代发器直接提交，不付打包费
- **私有代发器**：forum-sponsor 用自己的热钱包直接调用 EntryPoint 的 handleOps 提交本站用户的操作；提交前用 eth\_call 模拟，支持 100–200 ms 微批合并（将同窗口内多笔不冲突的 UserOperation 合并进一次 `handleOps` 数组提交，消除单热钱包 EOA nonce 并发排队并摊薄基础 gas），卡单自动提价重发。因为只处理自己用户的操作，不需要公共 Bundler 那套防滥用规则和付费追踪 RPC，也不付打包费
- **付款前的操作收代付费**：付款（含拍卖成交）、提回交易所、超时取回、`cancelOffer`、已部署钱包修改签名者等，收固定代付费（默认 0.05 USDT，站长可调）。代付费由 Paymaster 合约在 `postOp` 阶段直接扣取（依赖钱包部署 `initCode` 中预设的 Paymaster 授权或 EIP-2612 / ERC-1271 `permit`，不依赖业务 `callData` 里的临时 `approve`；ERC-4337 规定业务 `callData` 回滚后 `postOp` 照样执行）。业务失败也收得到，刷失败交易不再是零成本
- **付款后的操作结算时扣回**：标记发货、开始服务、确认收货、领取、和解（每单双方各限免费代付 1 次 `proposeEnd` + `acceptEnd`，超出收代付费）、延长确认期（`extendConfirm` 每单限免费代付 1 次）、确认期满放款由平台代付，结算时合约从托管款先扣固定 gas 费再分配；发起争议（`dispute`）已预付争议费，不再另收 0.05 USDT 代付费（见第 6 节）
- **代付签名服务单独运行**：forum-sponsor 是独立的 Rust 程序和系统用户（代付签名 + 私有代发），只有它持有 Paymaster 签名私钥（systemd-creds 加密）；只给白名单合约方法、符合规则的操作签字（校验前置状态时直接认链上 `latest` 状态，不等 `finalized`），签名 2 分钟内有效且绑定该笔操作；每个账户同一时间只批准一笔待上链的代付操作；同一账号链上失败次数过多自动暂停代付资格；执行失败的操作照样耗 gas，所以签字前必模拟、按账号和 IP 限频
- **次数上限**：每单标记发货 1 次、开始服务 1 次、延长确认期免费代付 1 次、和解提议每方免费代付 1 次、领取每天 1 次；合约同样限制两次领取至少间隔 24 小时且当次可领净额 > 领取 gas 费，保证每次扣的领取 gas 费都对应一次平台代付，卖家不会被重复收费
- **押金和热钱包只放少量 ETH**：Paymaster 押金按约 2 周用量存放，代发器热钱包只放少量 ETH；低于告警线通知站长从运营钱包补充（站长每两周在交易所或 DEX 把收到的 USDT 换成 ETH 补进押金；不做自动兑换，避免给服务器动用资金的权限）。私钥泄露最多损失这些 ETH，动不了任何用户资金
- **超时交易谁来发**：确认期满放款由 worker 自动发起，gas 从固定 gas 费扣回；卖家未发货的超时退款由买家在订单页点「取回」，按付款前规则收代付费，避免被小号反复刷退款消耗押金
- **故障备用**：私有代发器故障时自动切到第三方 Bundler，gas 始终由自己的 Paymaster 付；RPC 用普通档即可（不需要交易追踪），至少两家

## 6. 担保合约

担保由两份不可升级的合约负责（拍卖成交见本节末尾）：`Escrow`（一次性放款）和 `StreamEscrow`（分期放款），共用手续费、签名和权限代码，一起审计。钱只能流向该订单的买家、卖家，以及按规则扣除的手续费、gas 费和争议费；平台和任何管理员都转不走。

**部署**：只部署在 Arbitrum One；USDT（USD₮0）地址、6 位精度、最低手续费写在链配置里。

**订单状态**：`createAndFund` 一步建单即为 `Funded`（没有「已创建未付款」状态）→ 结束于 `Released`（放款）、`Refunded`（退款）、`Settled`（协商和解）之一；中途可进入 `Disputed`，再由裁决、和解或超时兜底结束。

**函数（两份合约通用部分）**

| 函数 | 调用者 | 作用 |
| --- | --- | --- |
| `createAndFund(offer, sellerSig)` | 买家 | 验证卖家报价签名，建单并转入 USDT（含买家应付的手续费与 gas 费） |
| `markDelivered` / `start` | 卖家 | 一次性：开始计算确认期；分期：开始解锁计时 |
| `release` | 买家 | 一次性：确认收货放款 |
| `claim` | 卖家 | 分期：领取已解锁部分 |
| `refund` | 卖家 | 卖家主动全额退款 |
| `proposeEnd` / `acceptEnd` | 买家或卖家 | 协商和解：一方提出退给买家的金额，另一方确认后执行；72 小时未确认失效 |
| `dispute` | 买家或卖家 | 发起争议并预付争议费（只由发起方付；卖家可直接用本单已解锁未领余额或可用保证金抵扣） |
| `resolve(orderId, toBuyerBps, bondToBuyerBps)` | 仲裁 Safe | 按比例裁决 |
| `claimTimeout` | 任何人 | 一次性：卖家已发货且确认期满 → 放款；未按期发货 → 退款。分期：开始期限已过未开始 → 退款 |
| `resolveTimeout` | 任何人 | 争议 30 天未裁决时按默认规则结算 |
| `withdraw(to)` | 有可领余额的本人 | 转账失败而留在合约的余额，转到自己指定的地址 |
| `cancelOffer(nonce)` | 卖家 | 作废已签出的报价 |
| extendConfirm(orderId, secs) | 卖家（或买家紧急顺延 1 次） | 卖家物流延误时延长买家确认期（累计上限写死）；买家在确认期最后 6 小时内可免费触发 1 次 24 小时紧急顺延（留出从交易所提币充争议费的时间） |
| createFromAuction(授权, 卖家签名, 成交证明, 平台签名) | 拍卖赢家 | 校验卖家拍卖授权与平台成交证明、付款人是赢家、成交价 ≥ 保留价、每场拍卖只成交一次，然后与 createAndFund 一样建单 |
| extendDeadlines(orderIds, secs) | 仲裁 Safe | 主站故障等紧急情况下批量延长未结订单的发货期、确认期（只能延长，单次 ≤ 7 天、累计 ≤ 14 天），不能动资金 |
| depositBond / withdrawBond | 卖家 | 在 `Escrow` 存入统一保证金池（同时供 `Escrow` 与 `StreamEscrow` 锁定）；只能取出未被任何订单锁定的可用部分 |

**卖家保证金（买家可要求）**

- **统一保证金池**：保证金统一存放在 `Escrow` 合约中，授权 `StreamEscrow` 调用锁定、解锁与赔付，卖家无需在两份合约分别存钱；用 `withdrawBond` 只能取出未锁定的可用部分，一笔余额可同时为多笔订单分别锁定
- **约定**：报价里多一个「卖家保证金」字段（0 = 不要求），买家在私信里提要求、卖家签名即同意；合约写死上限：不超过订单金额
- **锁定**：`createAndFund` 建单时同一笔交易里锁定，卖家可用保证金余额不够整笔回滚；没有「等卖家交保证金」的中间状态
- **解锁**：买家确认、确认期满放款、和解、仲裁判卖家胜时全额解锁回卖家可用余额
- **赔付**：仲裁判卖家责任时，`resolve` 多一个参数，可把锁定保证金的 0–100% 赔给买家（仍然只能给买卖双方）；卖家逾期不发货的超时退款，按报价约定的违约比例（默认 0）赔给买家，其余解锁
- **提额与认证基准**：换取更高单笔上限与认证标识（0 / 100 / 500 / 1000 USDT 四档）按**当前未锁定的可用保证金**（或总保证金扣除在途锁定后余额）核定，防止同一笔保证金无限接不锁保证金的大单
- **界面**：卖家主页显示保证金总额、可用余额和已锁定金额；报价卡片和付款确认页显示「卖家保证金 X USDT，将随订单锁定」
- **代价**：担保合约多 2 个函数和 1 个参数，审计范围随之增加，必须在第 12 周冻结前完成

**两种模式**

| 项目 | 一次性 `Escrow` | 分期 `StreamEscrow` |
| --- | --- | --- |
| 适用 | 实物、一次交付的数字商品 | 按时间提供的服务：租用、代运营、订阅 |
| 放款 | 买家确认或确认期满后全额放款 | 每个周期解锁「可解锁净本金 ÷ 期数」，卖家随时领取已解锁部分 |
| 周期 | — | 每小时 / 每天 / 每周 / 每月（按 30 天计），总时长 ≤ 365 天，单期金额 ≥ 0.1 USDT |
| 提前结束 | 双方同意可和解（如部分退款），否则只能争议 | 同左；任何一方都不能单方面停止 |
| 争议 | 冻结全部金额 | 发起争议时记录 disputedAt，之后解锁额度一律按 min(当前时间, disputedAt) 计算；裁决范围是全部未领取部分（含争议前已解锁未领取的，因为争议常常针对的正是这段服务） |

```
分期：可解锁净本金 = 订单金额 − 卖家承担的手续费与基础固定 gas 费（建单时单独划入订单费用池，不参与按期解锁）
      已解锁 = 可解锁净本金 × min(已过周期数, 总期数) ÷ 总期数   （已过周期数向下取整，余数归最后一期）
      可领取 = 已解锁 − 已领取                                   （每次 claim 须满足 可领取 > 0.02 USDT，当次直接从中扣 0.02 USDT 领取 gas 费）
```

**卖家报价（EIP-712 签名）**

- 内容：金额、模式、周期与期数、手续费承担方、gas 费、发货期限（或即时发货标记）与买家确认期（一次性）或开始期限（分期）、交易帖内容哈希、有效期、可成交次数（默认 1）、卖家保证金与逾期违约比例（可选）、指定买家（私信发起时自动指定为对方，报价被转给别人也用不了；公开报价不指定）、nonce；各期限必须在合约写死的范围内
- 签名域绑定 chainId 和合约地址，测试网与主网、新旧版本合约之间不能重放
- 卖家智能账户未部署也能签：合约用 ERC-6492 验签（基于 SignatureChecker，支持 ERC-1271）；卖家签了报价却没卖出，平台零成本
- 按报价哈希计数成交次数，用完即失效；卖家可随时 `cancelOffer`
- **交易帖内容锁定**：报价里带交易帖内容哈希，下单时论坛保存该版本快照；卖家之后编辑帖子不影响已成交订单，争议以快照为准，快照被改动也能用哈希发现
- **最高费率保护**：报价里写明卖家接受的最高费率和最高固定 gas 费；下单时当前参数超过它，合约直接拒绝，卖家早先签出的报价不会因调价被多扣

**费用**

```
手续费 = max(订单金额 × 费率, 1 USDT)        （USDT 6 位小数，1 USDT = 1,000,000 最小单位）
gas 费  = 基础固定额（如 0.1 USDT，含建单后发货/开始/放款/和解结算）；分期卖家每次 claim 另从当次领取额中扣 0.02 USDT
争议费 = 本单手续费 × 倍数（默认 1 倍，即与手续费相同；手续费为 0 的订单（如免费活动期间）按最低手续费计，保证争议不是零成本），由发起方预付
```

- 手续费与基础固定 gas 费的承担方由报价约定：卖家（默认）、买家或各半；各半时最低手续费也各付 0.5 USDT；分期每次 `claim` 的 0.02 USDT 固定从卖家当次领取额中扣除
- 最低订单金额 5 USDT（分期单期金额 ≥ 0.1 USDT）；卖家主动退款、未按期发货超时退款不收手续费；卖家从未做过链上操作的订单免收基础固定 gas 费
- 买家预付但未产生的手续费，在退款或和解时按比例退回
- 争议费：发起方胜诉全额退回、败诉全部进金库（对方不用付争议费）；按比例裁决则按比例结算。卖家发起争议时，合约优先从本单已解锁未领取余额或可用保证金中直接划扣争议费，无需卖家再从交易所充币。收了争议费就不另收手续费：该订单实收手续费 = max(0, 按结算应收的手续费 − 留存的争议费)，多预付的手续费退回给付的一方；发起方败诉时争议费等于手续费，订单不再收手续费，平台每单最多只收一份；争议中达成和解或 `resolveTimeout` 结算时全退
- 不设免争议费门槛：小额订单手续费低，争议费也随之很低
- Safe 批量执行裁决的 gas 由运营钱包支付，成本由争议费收入覆盖
- **费用池与 gas 费先留再分**：建单时手续费与基础固定 gas 费单独记入订单费用池（不进入分期可解锁本金，防止分期后半段发生争议或退款时剩余余额不够扣费导致算术下溢）；只要平台垫付过（标记发货、开始、领取、和解），结算时先从费用池扣基础固定 gas 费，剩余再按放款、退款、和解或裁决比例分配；即使最后判全额退款，平台垫付的 gas 也能收回
- **手续费限时免费活动**：金库 Safe 设置开始时间、结束时间、活动费率（0 即免费，最低手续费同时失效）和适用范围（担保 / 拍卖 / 全部）；活动期间新建的订单按活动费率写入快照（拍卖按成交建单时间），到期自动恢复，单次最长 90 天；可提前安排；提前结束等于涨价，同样 72 小时后生效。默认只免手续费、gas 费照收；站长可另开「gas 补贴」连 gas 一起免，补贴由运营钱包承担；补贴按订单数设上限并由合约计数（如前 1000 单），超过后新订单自动恢复收 gas，已享受补贴的订单后续操作平台照付，支出可提前算清。活动开始和结束时全站公告并推送 Telegram 频道

**超时兜底 `resolveTimeout`（争议 30 天未裁决）**

- 一次性：卖家未标记发货 → 全额退买家；已发货 → 未领取部分双方各 50%
- 分期：卖家从未开始 → 全额退买家；已开始 → 按争议发生时的解锁进度给卖家，其余未领取部分双方各 50%
- 争议费全退。保证多签失效或平台停摆时资金也不会永久锁死

**权限与参数**

- `arbiter` = 仲裁 Safe（2/3），只能调用 `resolve`；3 名签名人必须是不同的人，且担任签名人期间不审案（站长 + 2 名轮值资深仲裁员；超级管理员负责双人裁决分歧时的终裁，所以不当签名人），保证写裁决和执行裁决的不是同一批人；只执行后台已公示的裁决，交易数据带案件编号；当天裁决每天合并一笔批量执行
- `owner` = 站长控制的金库 Safe，只能调整费率（上限 10%）、最低手续费、最低订单金额、单笔上限（初期 200 USDT）、全站托管总额上限（初期 5000 USDT）、gas 费、争议费参数和收款地址；每个参数都有合约写死的上限，金库 Safe 也无法设出离谱数值；调高收费或收紧规则的修改 72 小时后才生效（期间全站公告），调低收费和免费活动立即生效；延迟由合约强制执行（新参数先排队，72 小时后自动生效，排队期间可撤销），不靠人工自觉；全部参数与默认值见第 9 节（`feeRecipient` = 金库）
- **所有参数在建单时写入订单快照**，修改只影响新订单
- 没有任何管理员提款函数、无代理升级、无 `selfdestruct`
- `pause` 只阻止新建订单，不影响已有订单的放款、退款、领取和超时处理

**安全实现**

- OpenZeppelin `SafeERC20`、`ReentrancyGuard`、`EIP712`、`SignatureChecker` + Solady ERC-6492；先改状态再转账
- **领取式转账**：放款、退款先记入可领余额再尝试转出，USDT 地址被冻结也不影响其他订单
- `createAndFund` 按实际到账余额变化记账，不信任传入金额
- 金额全用整数最小单位，费用按 bps 计算向下取整
- Foundry 单元测试、模糊测试、不变量测试（已领取 + 已退款 + 费用 + 合约余额 = 订单总额），行覆盖率 100%，Slither 无高危
- 不做付费审计（ADR 0007）：多方 AI 审计 + Halmos 符号执行 + 变异测试 + 4 周公开审查与漏洞赏金；主网初期单笔上限 200 USDT、全站托管总额上限 5000 USDT（合约强制）

**拍卖成交（P1）：拍卖期间不上链，结束后赢家与卖家 1 对 1 建担保订单**

出价全在论坛里进行，不经过合约、不花 gas、不用 Face ID。拍卖结束后，只有最高出价者和卖家之间建一张普通的一次性担保订单，发货、确认、争议、超时全部复用 `Escrow`。合约只多一个成交函数，不再有保证金和链上出价。

- **挂拍**：卖家一次 Face ID 用 EIP-712 签「拍卖授权」：拍卖编号、保留价、成交后的担保条款（发货期、确认期、手续费承担方、最高费率）、有效期；签名域绑定 chainId 和合约地址
- **出价**：加价幅度、保留价、防狙击顺延（默认结束前 15 分钟内有新出价就顺延 15 分钟，累计顺延上限 24 小时，站长在后台可调）由后端执行；出价记录只追加、公开可查
- **出价资格（卖家可选）**：不要求 / 钱包 USDT 余额 ≥ 出价的一定比例 / 余额 ≥ 固定金额；每次出价时读取出价人智能钱包余额校验，结束时再校验一次赢家。没有合约锁定，出价后钱仍可转走，所以这是「有钱才能出价」的门槛，不是担保
- **成交**：结束后 forum-sponsor 签一份「成交证明」（拍卖编号、赢家钱包地址、成交价、付款截止时间）；赢家一次 Face ID 调用 `createFromAuction` 付款建单。合约校验：卖家授权与平台证明都有效、付款人就是赢家、成交价 ≥ 保留价、同一场拍卖只能成交一次。卖家结束时不用再操作，也没法反悔
- **平台签名私钥被盗的最坏情况**：攻击者只能让某场拍卖以不低于保留价的价格卖给别人，付钱的是买家自己，卖家拿到的不低于保留价，资金转不走；私钥和代付私钥一样只在 forum-sponsor
- **赢家违约**：付款期（默认 48 小时）内不付款 → 记一次违约（信誉公开显示）并禁拍 30 天；次高出价者 24 小时内可按自己的出价成交（平台重新签成交证明）；仍无人成交则流拍，卖家免费重挂
- **防托价**：卖家本人账号不能出价；同设备、同 IP、同资金来源的关联账号出价标记并向其他用户提示；新账号单场出价设上限；违约记录和禁拍提高托价成本

## 7. 交易流程与争议

买家一次 Face ID 付款，卖家发货或开始服务，确认后放款；任何一步卡住都有超时、和解或仲裁兜底。

&#91;embedded content: 订单状态 · 付款后 3 种结局与兜底路径\]

没有「付款前取消」状态：下单即付款。买家没钱永远建不了合约：建单和转入 USDT 在同一笔交易里，余额不足时整笔回滚，链上不会出现空单；付款页先查余额，不足时只显示充值地址、不提交交易，forum-sponsor 签字前模拟也会拒绝，所以不会白扣代付费。私信里的报价卡片和拍卖成交只是签好的报价，买家付款成功那一刻才成为订单。付款后无论对方失联、平台停摆还是仲裁多签失效，资金都能经 claimTimeout 或 resolveTimeout 取回。

**一次性模式**

1. 买卖双方先在私信里谈好价格和条件（谁先发起都行：买家可发「担保请求」卡片并要求卖家保证金，不签名、不上链；卖家修改或接受后签名）（主要方式，和拍卖一样谈定后才建合约），卖家在会话里点「发起担保」，填价格、模式、期限、手续费承担方，签一份指定该买家的报价，以卡片发在会话里；标准商品也可以在交易帖预先签公开报价，任何人直接付款
2. 买家在交易所选 Arbitrum One 网络提币到钱包（报价卡片和付款确认页都写明：本单争议费多少、由发起方预付；卖家可直接用订单内已解锁余额或保证金抵扣争议费，买家付完货款后钱包通常是空的，若临近确认期满（最后 6 小时内）发现问题但钱包无余额，买家可先免费点 1 次「紧急顺延确认期 24 小时」再去交易所提币充争议费，防止提币延迟被超时放款。买家要求了保证金时同时显示卖家将锁定的金额），一次 Face ID 完成 `approve` + `createAndFund`
3. 卖家发货并点「已发货」，确认期开始；发货期限是最长期限，可以付款后马上发货。数字商品可在报价里选「即时发货」：卖家预先上传加密的卡密或下载链接，付款上链并经过数个区块确认（或 safe 标记，约数秒至数分钟，不等 20 分钟的 finalized）后系统自动向买家展示；合约建单时直接进入已发货状态、确认期立即开始，省去一次操作和 gas；内容无效时买家在确认期内发起争议
4. 买家确认收货或确认期满 → 放款（期满前 24 小时提醒买家，有问题须在期满前发起争议；物流延误时卖家可延长确认期，买家临期无余额充争议费也可免费紧急顺延 1 次 24 小时）；双方互评；卖家一键提回交易所
5. 有问题：先协商和解，谈不拢发起争议

**担保约定卡片：双方都确认才上链**

- 谁都可以先发：买家发「担保请求」，卖家发「担保报价」；卡片状态：待对方确认 / 已修改 / 已拒绝 / 已取消 / 已过期 / 已付款
- 收到卡片的一方可以：接受、修改约定（改价格、期限、手续费承担方、保证金等，变成新卡片回到对方确认，旧卡片作废）、拒绝（可附理由）；发起方在对方确认前随时可以取消
- 卖家的确认 = Face ID 签名（链下，不上链、不花钱）；买家的确认 = 付款。整个谈判只有买家付款那一笔上链，此时双方都已确认
- 作废的卡片（修改、拒绝、取消、过期）forum-sponsor 拒绝代付，付款按钮也消失；私信报价默认 24 小时有效（站长可调），过期后合约也不认；卖家担心已签名的报价在有效期内被用，可以付一次代付费在链上 `cancelOffer` 立即作废

**分期模式**

1. 卖家选周期和期数，例如 300 USDT、每天、30 期，订单页显示「每天 10 USDT」
2. 买家付款，全额锁入 StreamEscrow；卖家点「开始」后按周期解锁
3. 卖家随时领取已解锁部分；到期后 worker 可自动代领最后一笔
4. 提前结束必须双方同意（默认方案：已解锁归卖家、其余退买家，可协商修改），否则只能争议
5. 订单页进度条显示总期数、已过期数、已解锁、已领取、剩余可退
6. 争议会冻结解锁进度，裁决只能按比例结束订单、不能恢复分期；买家拿争议当「暂停键」没有好处：败诉要付争议费，冻结期间的服务费可判给卖家

**拍卖模式（P1）**

1. 卖家在拍卖板块发拍卖帖：起拍价、加价幅度、保留价、拍卖时长（在站长设定的范围内选，默认 24 小时–7 天）、出价资格（是否要求余额、要求多少），一次 Face ID 签拍卖授权
2. 买家出价：已开通交易即可，点出价就生效，不花 gas；有余额要求时先校验钱包余额；新出价经 WebSocket 即时显示，被超价的人收到站内和 Telegram 提醒
3. 结束前 15 分钟内有新出价就自动顺延 15 分钟（窗口、顺延时长和累计上限站长在后台可调）
4. 结束：达到保留价则平台签成交证明，赢家在付款期内一次 Face ID 付款，之后与一次性模式完全相同；未达保留价则流拍
5. 赢家逾期：违约记录 + 禁拍，次高出价者递补；卖家可免费重挂

**仲裁规则**

| 项目 | 规则 |
| --- | --- |
| 证据 | 订单聊天记录和建单前的私信谈判记录（系统保存，只关联发起担保的那个会话）、截图、物流单号 |
| 举证期 | 发起后 72 小时 |
| 裁决 | 举证期结束后 48 小时内由仲裁员裁决；≥ 200 USDT 双人独立裁决；可申诉一次 |
| 执行 | 仲裁员写裁决意见 → 仲裁 Safe 每天批量执行 |
| 结果 | 全额给买家、全额给卖家或按比例分；结果和理由对双方公开，脱敏后归入案例库 |

**仲裁员规则**

- 仲裁员由超级管理员从管理员中任命；与当事人有关联或 90 天内有交易的自动回避，案件随机分配
- 只看订单聊天（哈希链校验）、交易帖快照和双方证据；每次裁决写理由，进入审计日志，结果和理由对双方公开
- 大额争议（默认 ≥ 200 USDT）由两名仲裁员独立裁决，意见不一致由超级管理员终裁；超级管理员认为无法判断时升级为公开投票
- 任一方可在 72 小时内申诉一次，由未参与的仲裁员复核；复核结果为最终裁决
- 仲裁员只按工作量和按时率计酬，绝不与裁决方向挂钩；被推翻比例过高则暂停资格
- 裁决只是意见，链上执行由仲裁 Safe（3 人 2/3，签名人当期不审案）每天批量完成，只能把钱分给买卖双方

**无法裁决时升级为公开投票**

- **什么时候升级**：双人裁决意见不一致、超级管理员认为证据不足无法判断，或申诉复核人无法判断时，标记「无法裁决」并写明理由，案件自动进入公开投票
- **公开什么**：脱敏后的案情、交易帖快照、双方证据和仲裁员的分歧理由；不显示双方用户名、钱包地址和联系方式；争议规则里事先写明这一条
- **谁能投**：只有交易过的账号——至少完成 3 笔 ≥ 20 USDT 的担保交易、对手至少 2 个不同的人、注册满 30 天、无败诉和封禁记录；当事人、与当事人 90 天内有交易或关联（同 IP、同设备、邀请关系）的账号、管理人员不能投；一个账号一票，投票前要用钱包 Passkey 确认
- **怎么投**：选项为全额退买家 / 全额给卖家 / 各一半，必须写一句理由；投票期 72 小时，结束前不显示票数，避免跟风；当事人看不到谁投了什么，防止拉票和报复
- **怎么算**：至少 9 票才有效，得票最多的选项胜出；平票按各一半；72 小时不足 9 票顺延 48 小时，仍不足则按各一半结算
- **执行**：结果公示后由仲裁 Safe 按投票结果执行 `resolve`，签名人不得改判；合约不用改，投票全在论坛内完成、不花 gas；投票结果为最终结果，不能再申诉
- **投票人奖励**：每次有效投票 +5 经验，不发钱，也不按是否与多数一致奖励，避免为了拿奖励猜多数
- **时间内走完**：举证 72 小时 + 裁决 48 小时 + 申诉 72 小时 + 投票最多 120 小时，合计约 13 天，在 30 天 `resolveTimeout` 兜底之前完成
- **防刷票**：投票资格需要真实交易、付过手续费，养号成本高；同一案件中互有关联的投票账号只计 1 票，异常集中投票告警管理员群

**卖家保证金（P0，买家可要求）**：卖家把 USDT 存进 `Escrow` 合约的统一保证金池（供一次性与分期两份合约共用），买家要求保证金的订单在付款建单那一刻从中锁定（可用余额不够就建不了单）；订单正常结束自动解锁，仲裁判卖家责任时可把锁定部分赔给买家。未锁定的可用保证金余额也用于换更高的单笔上限和认证标识（如 0 / 100 / 500 / 1000 USDT 四档）。规则见第 6 节「卖家保证金」。

**账号交易成功率**

```
卖家成功率 = 成功订单 ÷ (成功订单 + 卖家责任失败订单)
```

| 订单结果 | 卖家统计 | 买家统计 |
| --- | --- | --- |
| 确认放款、确认期满放款、分期完整到期 | 成功 | 成功 |
| 双方协商和解 | 不计入，单独显示次数 | 同左 |
| 卖家未按期发货退款 | 失败 | 不计入 |
| 仲裁判卖家责任 | 失败 + 争议败诉 | 不计入 |
| 仲裁判买家责任 | 成功 | 失败 + 争议败诉 |

- 只统计链上订单结果，论坛改不了；每日从链上全量重算校对
- 显示「成功率 98.6% · 成交 214 笔 · 争议败诉 1 次 · 通常 10 分钟内回复」；不满 10 笔显示「新卖家 · 已成交 3 笔」
- 防刷：只计 ≥ 10 USDT 的订单；同一对买卖双方 30 天只计 1 笔；钱包、设备、IP 有关联的不计入并进入风控

**用户等级（和普通论坛一样，与手续费和合约无关）**

等级只影响论坛功能和显示，不减免手续费、不发券、不进合约；全部在后台配置。

| 等级（默认 6 级，可调 3–20 级） | 所需经验 | 默认权益 |
| --- | --- | --- |
| 1 新手 | 0 | 发帖、回复、私信（新账号限制见第 9 节） |
| 2 | 100 | 可发外链；点赞计入对方经验 |
| 3 | 500 | 私信每日上限提高、上传附件 |
| 4 | 2000 | 签名档、头像框 |
| 5 | 6000 | 发起投票、自定义头衔 |
| 6 | 15000 | 专属标识、可申请版主 |

- **经验来源**（分值和每日上限站长可调）：发主题 +2（每天计 5 帖，发出 24 小时未被删才计）；回复 +1（每天计 20 条，回自己的帖子、纯表情、重复内容不计）；被设精华 +50（撤销即扣回）；被点赞 +1（只计 2 级以上账号，每天计 20，同一对账号互赞只计一次）；完成交易 +10（订单 ≥ 20 USDT，同一对买卖 30 天只计 1 笔）；邀请有效新人 +20；违规删帖 −20、争议败诉 −100
- **等级不降**：经验只增不减（违规扣分除外），后台可手动调整，写审计日志
- **邀请防自己邀请自己**：被邀请人注册满 7 天、有 5 个以上未被删的帖子或回复、并与邀请人以外的人完成 1 笔 ≥ 20 USDT 交易，才算有效邀请；邀请人与被邀请人之间的交易、点赞、回复一律不计经验和信誉；同 IP 或网段、同设备指纹、钱包间直接转账、邮箱归一化后相同或一次性邮箱 → 转人工审核；每月最多计 10 个有效邀请；被邀请人 30 天内被封号则扣回，多次被扣回取消邀请资格
- 奖励只有经验，没有钱，刷邀请得不偿失

**订单即时通讯**

- 浏览器与 forum-api 保持 WebSocket；消息先写 PostgreSQL，再经 Valkey Pub/Sub 推给对方所有在线设备，不用刷新
- 30 秒心跳；重连后按最后一条消息 ID 补拉
- 文字、图片、系统消息（付款、发货、开始服务、和解提议、争议等自动插入）；已读、正在输入、对方在线
- 消息不能删改，争议时仲裁员可见全部历史；检测到钱包地址或「线下转账」时警示只走担保
- 只有双方和仲裁员能订阅会话；不做端到端加密（仲裁要读），传输全程加密
- 每条消息保存「上一条哈希 + 本条内容」的哈希链，裁决前校验，服务器上的聊天记录被改动可被发现

**在线状态**

- 有 WebSocket 连接即在线，30 秒心跳续期，90 秒过期；不在线显示「最近活跃：5 分钟前 / 今天 / 3 天前」
- 只在订单聊天和私信里实时推送上下线；列表页批量查询，停留时每 60 秒刷新
- 可隐身（只显示活跃到天），但进行中订单的交易对手仍能看到真实状态

## 8. 数据库设计

PostgreSQL 18 单库承载全部数据（2000 万帖子约 40–80 GB 含索引）。核心原则：每个高频页面恰好一次索引查询，翻到第 1 页和第 5000 页一样快。SQL 用 sqlx 在编译期检查（离线元数据进仓库），迁移用 sqlx migrate，只增不改。

**热路径与索引**

| 页面 / 操作 | 查询方式 | 索引 | 预期 |
| --- | --- | --- | --- |
| 板块帖子列表 | 置顶帖单独缓存只在第 1 页顶部展示；普通帖前 200 页从 Valkey 有序集合取主题 ID 再按主键批量取，更深按 (last\_post\_at, id) 游标 | `topics (forum_id, last_post_at DESC, id DESC) WHERE (flags & 9) = 0`（排除隐藏帖与置顶帖，保证 ZSET 与深分页游标语义一致） | < 5 ms |
| 帖子第 N 页 / 跳页 | `floor BETWEEN (N-1)*20+1 AND N*20` | `posts (topic_id, floor)` 唯一 | < 5 ms |
| 用户主页帖子 | 游标 | `posts (author_id, id DESC)` | < 5 ms |
| 通知 | 游标 | 按月分区 `(user_id, created_at DESC)` | < 3 ms |
| 订单聊天 | 游标 | `order_messages (order_id, id)` | < 3 ms |
| 我的订单 | 游标 | `escrow_orders (buyer_id, id DESC)`、`(seller_id, id DESC)` | < 5 ms |
| 用户名片 | 整页批量取 | Valkey 哈希缓存，未命中查主键 | < 1 ms |
| 全文搜索 | PGroonga | 帖子纯文本列 | p95 < 300 ms |

**核心表结构**

```sql
CREATE TABLE topics (
  id             bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  forum_id       int         NOT NULL,
  author_id      bigint      NOT NULL,
  title          text        NOT NULL,
  kind           smallint    NOT NULL DEFAULT 0,  -- 普通 / 交易 / 争议
  flags          smallint    NOT NULL DEFAULT 0,  -- 1=置顶、2=精华、4=锁定、8=隐藏
  last_floor     int         NOT NULL DEFAULT 1,  -- 最大楼层 = 回复数 + 1
  last_post_id   bigint,
  last_poster_id bigint,
  last_post_at   timestamptz NOT NULL,
  created_at     timestamptz NOT NULL DEFAULT now()
) WITH (fillfactor = 80);
CREATE INDEX topics_forum_list ON topics (forum_id, last_post_at DESC, id DESC) WHERE (flags & 9) = 0;
CREATE INDEX topics_forum_pinned ON topics (forum_id, id DESC) WHERE (flags & 1) != 0 AND (flags & 8) = 0;

CREATE TABLE posts (
  id         bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  topic_id   bigint      NOT NULL,
  floor      int         NOT NULL,
  author_id  bigint      NOT NULL,
  html       text        COMPRESSION lz4 NOT NULL,  -- 发帖时已过滤渲染
  plain_text text        NOT NULL,                  -- 供全文搜索
  status     smallint    NOT NULL DEFAULT 0,        -- 删除只改状态，楼层保留
  created_at timestamptz NOT NULL DEFAULT now(),
  edited_at  timestamptz,
  UNIQUE (topic_id, floor)
);
CREATE INDEX posts_author ON posts (author_id, id DESC);
CREATE INDEX posts_search ON posts USING pgroonga (plain_text);
CREATE TABLE post_sources (post_id bigint PRIMARY KEY, source jsonb NOT NULL);  -- 编辑器原稿
```

**其余表（关键字段）**

| 分组 | 表 |
| --- | --- |
| 账号 | users（含 last\_seen\_at、show\_online）、passkeys、wallets (chain\_id, address)、withdraw\_addresses（含生效时间）、sessions 存 Valkey |
| 论坛 | forums、topics、posts、post\_sources、notifications（按月分区，保留 180 天）、messages、user\_levels、exp\_ledger（经验流水，只追加）、invites |
| 交易 | chains（链配置：RPC、合约与 USDT 地址、精度、最低费用、确认块数）、trade\_listings、offers、escrow\_orders（chain\_id、chain\_order\_id、amount、gas\_fee、mode、interval\_secs、periods、released\_amount、state、参数快照）、escrow\_events (chain\_id, tx\_hash, log\_index) 唯一 |
| 拍卖 | auctions（listing\_id、起拍价、加价幅度、保留价、出价资格、end\_at、当前最高价与出价人、state、卖家授权签名）、auction\_bids（只追加，索引 (auction\_id, id DESC)）、auction\_defaults（违约与禁拍）；由 forum-api 写入，成交后的订单仍由 indexer 写入 |
| 聊天与信誉 | order\_messages、order\_message\_reads、user\_trade\_stats |
| 争议 | disputes、dispute\_evidence、dispute\_reviews（申诉复核）、dispute\_votes（公开投票，只追加） |
| Telegram | telegram\_links、telegram\_bind\_tokens、channel\_posts |
| 管理与资金 | staff\_roles、admin\_audit\_logs（只允许插入，数据库层面撤销所有账号的改删权限）、staff\_compensation、staff\_work\_stats、payout\_batches、payout\_items、treasury\_expenses、budget\_allocations、treasury\_reports |
| 基础 | outbox（事务发件箱）、apalis 任务表 |

**规则**

- 主键一律 bigint 自增，不用 UUID；链上金额 NUMERIC(38,0) 存最小单位（统一用 NUMERIC，以后换资产也不会溢出）
- 回帖在同一事务里 `UPDATE topics SET last_floor = last_floor + 1 … RETURNING` 分配楼层：HTML 过滤在事务外完成，分配楼层、插入 `posts`、插入 `post_sources`、写 `outbox` 发件箱合成一条多 CTE 语句一次发出并立即提交，热帖抢楼时行锁只持有亚毫秒；只有浏览数先记 Valkey，每 10 秒批量回写
- 帖子表不分区（2000 万帖子的 B-tree 索引合计约 2 GB，可常驻内存；PGroonga 索引另计）；通知、审计日志、链上事件按月分区，只追加的大表时间列用 BRIN 索引；帖子超过 2 亿再按 id 分区归档
- 列表一律游标或楼层定位，禁止大 OFFSET
- 各程序用独立数据库账号：只有 indexer 能写订单与链上事件等派生表
- user\_trade\_stats 由 indexer 更新，每日从链上重算校对
- **区块回滚**：链上事件表带 block\_number、block\_hash 和确认级别标记；latest 事件立即写入并触发界面更新与即时通知（注明「已上链」），每 5 秒校对时发现区块哈希与主链不符，就撤销未确认记录、重放并补发状态修正通知；数字商品自动发卡密等数个块确认（或 safe 标记）；到 RPC 的 finalized 标记后置为最终确认，财务记账、交易信誉统计、经验与薪资只认最终确认记录

**搜索**：PGroonga 中文无需词典、索引实时更新；只索引纯文本；结果最多 1000 条，搜索接口单独限流。阶段 1 在真实数据量下与 zhparser 对比后定案。

**缓存（Valkey）**

| 缓存 | 内容 | 失效 |
| --- | --- | --- |
| 板块列表 | 每板块一个置顶帖列表 + 一个普通帖有序集合（最新 1 万个非置顶主题 ID） | 发帖、回帖、置顶变更时更新 |
| 主题第 1 页 | 主题信息 + 前 20 楼 | 该页变化时删除 |
| 用户名片 | 用户名、头像、等级、信誉、在线 | 变化时删除 |
| 游客页面 | 整页 HTML，Cloudflare 缓存 60 秒；只有带有效会话 Cookie 的请求才绕过缓存（Cookie 带 HMAC 签名，Next.js middleware 验签，伪造的当游客处理，直接返回 Valkey 里的游客页） | 自动过期 |

**PostgreSQL 参数（生产 8 核 32 GB NVMe；测试服务器另有一套，见第 13 节）**

| 参数 | 值 | 原因 |
| --- | --- | --- |
| shared\_buffers / effective\_cache\_size | 8GB / 20GB | 内存 1/4 给数据库缓冲 |
| work\_mem / maintenance\_work\_mem | 32MB / 1GB | 防止并发爆内存；建索引更快 |
| random\_page\_cost / effective\_io\_concurrency | 1.1 / 200 | NVMe 随机读接近顺序读 |
| default\_toast\_compression / wal\_compression | lz4 / zstd | 压缩更快、写放大更小 |
| max\_wal\_size / checkpoint\_timeout | 8GB / 15min | 减少检查点抖动 |
| jit / huge\_pages | off / on | 短查询不需要 JIT；降低页表开销 |
| max\_connections | 150 | 各程序连接池合计约 60 |
| autovacuum（热表） | scale\_factor 0.02 | 热表更早清理，避免膨胀 |

开启 pg\_stat\_statements 和 auto\_explain（> 50 ms 自动记录执行计划）。

## 9. 管理体系与平台资金

> **已修订（ADR 0013）**：角色简化为**站长**（合并原超级管理员）、**管理员**（含仲裁，不再设单独仲裁员）、**版主**。管理员与版主用邮箱登录直接在论坛管理；只有站长进后台；提交仲裁裁决时用 Passkey 确认；仲裁 Safe 为 2 名管理员 + 站长中任意 2 人签名（平时两名管理员执行，意见不一致时站长终裁）。下文角色表与账号规则中与此冲突之处以 ADR 0013 为准。

**角色**

| 角色 | 人数 | 能做 | 不能做 |
| --- | --- | --- | --- |

**管理人员账号规则**（ADR 0013 已修订：角色简化为站长（合并超级管理员）、管理员（含仲裁）、版主；管理员与版主用邮箱登录直接在论坛管理；只有站长进后台、以及提交裁决时需要 Passkey；仲裁 Safe 签名人为站长 + 2 名管理员。本节及第 7 节与此冲突的内容以 ADR 0013 为准）

- 只能用 Passkey 登录（邮箱登录对其禁用）；站长、超级管理员、管理员至少 2 个 Passkey，版主和仲裁员 1 个即可；硬件安全密钥可选不强制
- **站长和超级管理员必须是两个不同账号**（系统强制），同一人兼任也要分开
- 敏感操作（任免、封号、隐藏证据、发薪、拨预算、改设置）前再验证一次 Passkey，5 分钟内可连续处理
- 会话闲置 2 小时过期、最长 12 小时；后台独立子域名 + 异常登录告警（不设 IP 白名单，管理人员多在手机上处理）
- 封号、删帖等选择预设理由（可补充说明）写入审计日志；被处理用户可申诉，由另一名管理员处理
- 超级管理员的每个操作实时推送到 Telegram 管理员群；超级管理员失联或被盗时，由站长撤销角色、取回薪资钱包余额并指定新人
- **站长账号找回**：站长丢失全部 Passkey 时，只能由持有服务器 SSH 密钥的人在服务器上执行一次性找回命令，生成 15 分钟有效的重新绑定链接；写入审计日志并通知管理员群。其他管理人员由上级在后台重置。平台资金不受影响，因为 Safe 签名设备与后台登录无关

**平台钱包**

| --- | --- | --- | --- |

**薪资与报酬发放**

- 薪资 = 固定月薪 + 工作量奖励（处理举报、审核证据、裁决案件、按时率）− 扣减（申诉被推翻、超时）
- 仲裁员只按工作量和按时率计酬，绝不与裁决方向挂钩；被推翻比例过高则暂停资格
- 每月 1 日系统生成草稿 → 超级管理员 3 日内审核 → Passkey 签名一笔批量转账，当月薪资同一笔发出 → 交易哈希写入工资单
- 收款地址默认本人钱包，可改专用地址（Passkey 确认 + 24 小时冷却）；明细只对本人、超级管理员、站长可见；薪资标准修改推送管理员群并入审计日志
- 上线初期按同样规则手动整理清单发放，统一发放模块（薪资、活动奖励共用）放在上线后迭代

**记账与报表**

- 收入不手工录入：indexer 从链上统计进入金库和薪资钱包的金额，自动对账
- 金库和运营钱包的每笔支出登记类别、用途、凭证和交易哈希；法币付款的账单记录兑换和付款凭证
- 每月自动生成财务报表（收入、支出、薪资、结余），只有站长可见；Paymaster 与热钱包余额低时告警给站长
- **平台钱包异常支出告警**：Safe 本身不认识工资单，超级管理员可以绕过后台直接在 Safe 里转账。所以 indexer 监控三个 Safe 的每笔支出：薪资钱包转出不对应已批准的工资单、运营钱包超出预算类别时，立即告警站长并推送管理员群。「不能给自己发薪」靠后台拦截 + 此告警 + 薪资钱包只放当月预算三重保证

**站长可配置参数与默认值**

能配置的尽量交给站长。链上参数由金库 Safe 修改，只能在合约写死的范围内调，建单时写入快照，提高收费或收紧规则 72 小时后生效；链下参数由站长在后台修改（Passkey 再验证、写审计日志、推送管理员群），其中影响用户的规则变更自动发公告。

## 10. Telegram 集成

Telegram 只做通知、讨论和引流，任何涉及资金或账号安全的操作只给「去论坛处理」按钮；Telegram 账号被盗也动不了钱。

**机器人**

- 绑定：论坛生成一次性链接（10 分钟、只能用一次）→ 打开机器人自动发送 `/start <令牌>` → 完成；解绑立即删除 Telegram ID 并移出群
- 通知（P0）：回复、@、私信、订单状态（付款、发货、开始、和解提议、争议进展）；每类单独开关，可设勿扰时段
- 订单消息默认只提示「有新的订单消息」，用户可选择显示预览
- 快速回复（P1）：直接回复私信和订单消息，同步到论坛并标注「来自 Telegram」；订单进入争议后关闭

**官方频道（P1）**：推送公开板块的新主题和精华帖，交易帖和争议帖默认不推；帖子删除时同步删除；高峰时合并成每 10 分钟一条汇总。

**官方群聊（P1）**：申请制，入群链接只在论坛内展示；机器人只批准已绑定、注册满 7 天、账号正常的用户；论坛封号、禁言或解绑时自动移出或禁言；删除含钱包地址或「私下转账」的消息并提醒走担保。

**管理员群**：超级管理员操作、薪资标准变更、异常告警实时推送。

**实现与安全**

- teloxide；生产用 Webhook（forum-api 接收并校验密钥头），本地开发用轮询；消息经 apalis 队列由 worker 发送，遵守 Telegram 限速（全局约每秒 30 条，单群每分钟 20 条）
- 机器人令牌只存服务器加密配置，可随时吊销重发
- 官网和机器人简介公布官方机器人用户名，提醒官方永远不会私聊索要恢复码或要求私下转账

## 11. 安全

服务器即使被完全攻破，攻击者也拿不到托管资金、金库或任何用户私钥；最大的真实风险是借服务器或 XSS 下发假页面骗用户签名，所以钱包和后台页面与服务器隔离部署。

**用户与交易风险**

| 风险 | 措施 |
| --- | --- |
| XSS 伪造交易 | 钱包、后台独立子域名并部署在 Cloudflare Pages；严格 CSP；帖子 HTML 服务端 ammonia 过滤、前端 DOMPurify 二次过滤 |
| 签名内容被误导 | 动钱前先显示确认页（动作、金额、网络、地址前后 6 位）再调 Face ID |
| 合约漏洞 | 简单状态机、OpenZeppelin、模糊与不变量测试、多方 AI 审计、Halmos、公开审查、单笔与总额上限、漏洞赏金（ADR 0007） |
| 仲裁作恶 | 仲裁 Safe 3 人 2/3 签名，只执行已公示裁决；`resolve` 只能分给买卖双方 |
| 刷 gas 代付 | 只给白名单方法代付、签字前模拟、代付费预扣或结算扣回、每单次数上限、按账号和 IP 限频 |
| 刷帖、广告 | Turnstile、Valkey 滑动窗口限流、新号限制、敏感词 |
| 盗号 | 普通用户无密码可撞；资金与敏感操作必须 Passkey；提币地址冷却 |
| 充错网络 | 只展示 Arbitrum One 并强警示；其他 EVM 链可找回，TRC20 不可 |
| USDT 地址被冻结 | 领取式转账 + `withdraw(to)`；订单尽快结算 |
| 诈骗与违规商品 | 信誉、新卖家上限、违禁品类目、举报、大额人工审核 |
| DDoS | Cloudflare 代理，源站只放行 Cloudflare IP |
| 论坛页面诱骗钱包签名 | 钱包 Passkey 的 RP ID 是钱包中心域名、关联域名里不含论坛主站，论坛主站和服务器被攻破都无法请求钱包签名（第 5 节） |
| Passkey 同步账号（Apple / Google）被盗 | 提币冷却目前只在页面上，攻击者用自写页面可绕过；先用每笔转出即时邮件和 Telegram 通知兜底，P1 给钱包加链上限额模块：转到新地址超过限额延迟 24 小时、本人可取消 |

**平台自身安全**

| 风险 | 措施 |
| --- | --- |
| 服务器被入侵 | 钱包与后台页面由 CI 构建后部署到 Cloudflare Pages，不经服务器；产物签名校验；关键文件完整性监控 |
| 后台账号被盗或内部作恶 | 仅 Passkey 登录 + 再验证 + 异常登录告警；最小权限；只增审计日志；资金只走 Safe |
| 信誉被篡改 | 每日从链上重算校对 |
| 数据泄露 | 磁盘、数据库、备份全加密；证据图片签名访问且有时效；数据保留期 |
| 依赖投毒 | 锁定版本；cargo-audit、cargo-deny、clippy、npm audit；Renovate 升级必须 CI 全绿；钱包前端依赖尽量少 |
| WebSocket 被刷 | 每用户、每 IP 连接上限；未登录不建长连接 |
| 部署通道被利用 | 部署账号只能执行固定安装脚本；只安装本仓库 CI 签名的产物；生产发布需人工批准 |
| 代付被刷 | 只给白名单方法签字、签字前模拟、代付费由 Paymaster 预扣（业务失败照收）、按账号和 IP 限频；押金只放 2 周用量，异常消耗告警 |
| 绕过 Cloudflare 直连源站 | Authenticated Origin Pulls：Caddy 只接受带 Cloudflare 客户端证书的连接；真实 IP 只信任来自 Cloudflare 网段的 CF-Connecting-IP |
| 第三方 Bundler / RPC 密钥被盗刷 | 密钥只在服务器，浏览器经 forum-api 代理；服务商后台设每月消费上限和告警 |
| 伪造 Cookie 穿透缓存打垮 Next.js | 会话 Cookie HMAC 验签，伪造的当游客返回缓存页；Cloudflare 对带 Cookie 的动态页按 IP 限流；Caddy 限制 Next.js 最大并发，超出排队或返回 503，不会被撑到内存溢出 |
| 服务器被攻破后告警被一并关掉 | 独立监控不跑在自有服务器：Cloudflare Workers 定时任务（或 Tenderly 告警）直接查链，盯金库与三个 Safe 每笔支出、合约 owner 变更、参数排队、Paymaster 押金余额；告警直发 Telegram 与邮件 |

**系统里所有的钥匙**

| 钥匙 | 保存在 | 能做什么 |
| --- | --- | --- |
| 用户 Passkey | 用户手机或电脑 | 只有本人能动自己的钱 |
| 用户恢复码（P1） | 用户离线保存 | 更换签名者，48 小时后生效 |
| 管理人员 Passkey | 各自设备 | 后台操作 |
| Safe 签名设备 | 站长、轮值仲裁员（仲裁 Safe）、超级管理员（薪资 Safe）各自设备 | 达到签名数才能动平台钱 |
| 第三方 API 密钥 | 服务器，加密配置 | RPC、Bundler、邮件、Telegram |
| Paymaster 签名私钥 | 服务器 forum-sponsor，systemd-creds 加密 | 只能批准代付，泄露最多耗尽 Paymaster 押金；押金提取权在运营 Safe |
| 代发器热钱包私钥 | 服务器，systemd-creds 加密 | 只放少量 ETH，提交所有操作（含 worker 发起的超时结算）；全系统只有这一个热钱包 |

**Web 安全基线**：会话 Cookie 规则见第 5 节；CSRF 用 SameSite + 写操作校验 Origin，钱包子域名调 API 的 CORS 只放行该子域名；CSP、HSTS、禁止钱包页被嵌入；上传限制类型大小、服务端重编码并清除 EXIF；服务端不抓取用户提供的任意网址；以 OWASP ASVS 第 2 级为标准。

**应急预案**

1. 合约或资金风险：owner Safe 立即 `pause`（只停新订单），站内公告
2. 服务器入侵：切维护页、吊销全部会话、轮换所有密钥（含 Paymaster、Telegram、热钱包），从干净备份重建
3. 前端被篡改：Cloudflare Pages 回滚到上一个签名版本
4. 72 小时内公开事故报告

**备用仲裁通道（主站被打死或服务器宕机时）**

仲裁的执行本来就不依赖服务器（仲裁 Safe 直接在链上调用 `resolve`），真正依赖服务器的是证据、登录和代付 gas。备用通道把这三样都放到服务器之外，主站停多久都能继续举证和裁决：

- **备用仲裁站**：独立域名（与主域名分开注册、不同注册商），Cloudflare Pages 静态页面 + Cloudflare Workers 小后端 + R2 存储；代码在同一仓库，CI 同时部署；平时只读，主站故障时站长用 Passkey 一键切换为可写；域名提前写进帮助中心、订单确认邮件和 Telegram 机器人简介
- **证据实时备份（信封加密）**：建单前的私信谈判记录、订单聊天、争议证据和裁决记录写入主库的同时，用每单独立对称密钥加密复制到 R2，而该对称密钥用备用站仲裁主公钥（及分配后的当值仲裁员公钥）做信封加密一并存入元数据；即使主站在发起争议前就已宕机，备用站接管并分配仲裁员后仍能解密完整历史记录
- **登录不依赖论坛**：用户在备用站用钱包 Passkey 签名登录（Worker 经 RPC 调智能账户的 ERC-1271 校验），仲裁员用后台 Passkey 登录；论坛数据库挂了也能用
- **备用代付**：Worker 内置备用代付签名（单独密钥，只批准 `dispute`、`claimTimeout`、`withdraw(to)` 和提回交易所，每日总额上限），经第三方 Bundler 提交；用户也可以选择自付少量 ETH
- **执行**：仲裁员在备用站提交裁决意见，仲裁 Safe 签名人直接在 Safe 官方界面签 `resolve`，全程不经过自有服务器
- **期限保护**：合约新增 `extendDeadlines`，主站故障期间仲裁 Safe 可把受影响订单的发货期、确认期统一延长（只能延长，单次 ≤ 7 天、累计 ≤ 14 天，不能动资金），避免用户因打不开主站被动超时；`resolveTimeout` 30 天仍是最终兜底
- **切回主站与演练**：主站恢复后，先将备用站切回只读，运行回流脚本将故障期间在 R2 新增的证据、聊天记录（延续原哈希链）和裁决合并回主库 PostgreSQL 与只增审计日志，校验无误后再恢复主站写入；上线前演练一次，之后每季度一次

**全流程闭环检查**

| 环节 | 正常路径 | 卡住或出错时 |
| --- | --- | --- |
| 注册 / 开通交易 | 邮箱注册；交易时开通 Passkey、钱包（P1 加恢复码） | Passkey 丢失用云同步或第二设备；域名丢失：P1 恢复码上线前无法签名（已知残余风险，ADR 0007） |
| 充值 | 交易所选 Arbitrum One 网络提币 | 选错 EVM 网络可找回；TRC20 无法找回，强警示 |
| 报价 | 卖家签名报价 | 改价下架用 `cancelOffer`；过期或成交次数用完自动失效 |
| 付款 | 一次 Face ID `createAndFund` | 私有代发器故障时切到第三方 Bundler，gas 始终由自有 Paymaster 付 |
| 发货 / 开始 | 卖家标记 | 卖家逾期不动：超时全额退款 |
| 确认 / 领取 | 买家确认；分期随时领取 | 买家不确认：确认期满自动放款；分期到期 worker 代领 |
| 提前结束 | 双方和解 | 一方不同意：争议 |
| 争议 | 举证、仲裁员裁决（大额双人、可申诉，无法裁决转公开投票）、Safe 执行 | 30 天未裁：`resolveTimeout` |
| 到账 | 转入对方钱包 | 地址被冻结：`withdraw(to)` |
| 提回交易所 | 一键转到已保存地址 | 盗号改地址：Passkey 确认 + 冷却 |
| 论坛停摆 | — | `claimTimeout`、`resolveTimeout` 任何人可调用；用户在 Cloudflare Pages 上的钱包「紧急取回」页用 Passkey 签名取回资金（不依赖服务器，ADR 0007；P1 起也可用恢复码在任何钱包工具取回）；此时没有平台代付 gas，需先往钱包地址转少量 ETH（几美元即够几十次操作），帮助中心和恢复码页面写明步骤 |
| 拍卖 | 论坛内出价，结束后赢家与卖家 1 对 1 建担保订单 | 赢家不付：违约记录、禁拍、次高者递补；卖家不发货：订单超时退款 |
| 主站被打死 / 服务器宕机 | — | 切到备用仲裁站：证据从 R2 备份读取，钱包 Passkey 登录，备用代付提交争议；仲裁 Safe 照常执行 resolve，必要时 extendDeadlines 延长期限 |

技术手段无法完全消除的风险：合约未知漏洞（靠多方 AI 审计、公开审查、单笔与总额上限、灰度）、仲裁员判断质量（靠大额双人裁决、申诉复核、无法裁决时公开投票和裁决理由留档）。

## 12. 性能

性能用硬指标约束，每次发版前用 k6 按设计容量压测，不达标不发版；页面速度指标是体验要求，不随在线人数降低。

**指标（3000 在线、峰值 1200 请求/秒、2000 万帖子；另做一次 2 倍压力确认余量）**

| 指标 | 目标 |
| --- | --- |
| 帖子页、板块页 API | p95 < 50 ms，p99 < 150 ms |
| 发帖、回复写入 | p95 < 100 ms |
| 聊天消息端到端 | p95 < 300 ms |
| 在线状态、通知推送 | < 1 秒 |
| 全文搜索 | p95 < 300 ms |
| 链上事件进入论坛 | < 3 秒（RPC WebSocket 订阅即时推送，每 20 秒批量补拉校对） |
| 首屏 LCP（移动 4G） | < 2.5 秒 |
| 单页首次加载 JS | < 200 KB（钱包 SDK 只在钱包页加载） |
| 峰值 CPU / 内存 | < 70% / < 80% |
| 可用性 | 上线初期 99.5%；加热备机后 99.9% |

**做法**

- 每条新 SQL 附 EXPLAIN 并命中索引，> 50 ms 记慢查询并告警；禁止 N+1，列表页的用户、在线、信誉一律批量取
- 三层缓存：Cloudflare（游客页）→ Valkey（热点）→ PostgreSQL，写入时精确失效
- 关键代码（费用计算、权限判断、消息分发）用 cargo bench 基准测试，CI 中性能下降超过 10% 即失败
- 链上状态两级：界面按最新区块即时显示「处理中」；资金、信誉、薪资只认最终确认的区块
- 发帖、聊天都是短事务，通知写入发件箱由 worker 异步发送

**图片处理（在自有服务器完成，不用按次计费的云服务）**

1. 浏览器先把超大图缩到最长边 2560px
2. 申请预签名地址，直传 R2 临时目录（JPG、PNG、GIF、WebP、HEIC，≤ 10 MB）
3. worker 取回原图：按内容校验真实格式 → 清除 EXIF（含 GPS）→ libvips 转 WebP（质量 80）
4. 生成 320 / 1280 / 2560 三种尺寸；动图转动态 WebP；HEIC 统一转换
5. 存正式目录、删除原图；文件名用内容哈希，Cloudflare 缓存一年
6. 处理中显示占位，通常 1 秒内完成；转换限 2 个 CPU 核并降低优先级

**邮件发送（Resend API + SMTP 双通道）**

- 统一「发邮件」接口，两种实现：resend-rs（Resend API）和 lettre（任意 SMTP 服务）；主通道失败自动切到备用并告警
- 所有邮件经发件箱由 worker 发送，失败指数退避重试，不重复发；验证码走高优先级队列，目标 10 秒内送达，通知可合并成摘要
- 接收 Resend 退信和投诉回调（校验签名），停发失效邮箱，保护发信域名信誉
- 模板（HTML + 纯文本）只写一份；发信域名配置 SPF、DKIM、DMARC；开发环境用 Mailpit 截获

所有服务在一台裸机上用 systemd 管理；Rust 程序编成单个静态可执行文件（musl），服务器上不装编译工具，只有 Next.js 需要 Node.js 运行时。

| Valkey | 2 | 开启 AOF |
| forum-api ×2（Rust） | 1 | Caddy 负载均衡，轮流重启不停机 |
| forum-worker（Rust） | 1 | 含图片转换（限 2 核） |
| forum-indexer（Rust） | 0.4 |  |

| forum-sponsor（Rust） | 0.1 | 代付签名 + 私有代发，独立系统用户 |
| 系统余量 | 7.8 |  |

**运维清单**

- Debian 13，自动安全更新；防火墙只开 80/443（仅 Cloudflare IP）和 SSH（密钥、非默认端口）
- PostgreSQL、Valkey 只监听本机 Unix socket；每个服务独立低权限用户，systemd 给应用设 `MemoryMax`（PostgreSQL 只设 `MemoryHigh`）、`ProtectSystem=strict`、`NoNewPrivileges`
- 密钥用 systemd-creds 加密存放
- 备份：pgBackRest 连续归档到 R2（加密），保留 30 天；每月恢复演练；R2 开启对象版本
- 服务器初始化写成 Ansible 脚本，一键重建
- 告警：CPU、内存、磁盘、慢查询、API 错误率、indexer 落后区块数、Paymaster 与热钱包余额、邮件通道故障
- 单链：indexer 一个实例；至少两家 RPC 自动切换；以后要加链 = 部署合约 + 新增链配置 + 启动 indexer，不改业务代码
- 独立监控：Cloudflare Workers 定时任务每分钟直接查链，与服务器告警互为备份（见第 11 节）
- 合约迁移：合约不可升级；发现漏洞时 owner Safe 暂停旧合约的新订单 → 部署新合约 → 旧订单在旧合约里照常走完（超时与仲裁不受影响）；indexer 和前端同时识别新旧合约地址；上线前在测试网演练一次

**三种开发与测试环境**

| 环境 | 配置 | 用途 |
| --- | --- | --- |
| 本机 WSL2 | 32 GB、2 TB NVMe | 日常开发（Anvil 本地链、Docker 跑 PostgreSQL / Valkey、Mailpit）；灌 2000 万帖子验证单条查询耗时和执行计划 |

测试服务器内存：PostgreSQL 4 GB（shared\_buffers 2 GB，模拟数据 200 万帖子）、Next.js 1.5、监控 0.8、测试网 indexer 0.3、forum-api 单实例 0.5、Valkey 0.5、worker 0.3、Caddy 0.1，余量约 4 GB；数据库参数单独一套。

本机 WSL 设置：`.wslconfig` 分配约 24 GB 内存；代码和数据放 WSL 自己的文件系统（如 `~/forum`），不放 `/mnt/c`；`wsl.conf` 开启 systemd；Windows Defender 排除 WSL 虚拟磁盘；手机测 Face ID 用 Cloudflare Tunnel 开发子域名（单独的 Passkey RP ID）；Telegram 本地用轮询。压测工具和服务在同一台电脑会抢 CPU，整体吞吐数字以生产规格为准。

**CI/CD（GitHub Actions 编译，服务器不编译）**

| 触发 | 做什么 |
| --- | --- |
| 每个 PR | 第 14 节全部质量门禁；任何一项失败不能合并 |
| 合并到主分支 | Rust 编成静态可执行文件（musl），Next.js 打包 standalone，钱包与后台用 Next.js 静态导出；自动部署到测试服务器和 Cloudflare Pages 预览环境 |
| 打版本标签 | 同一份产物部署生产，需在 GitHub Environments 由指定人员批准 |

- Rust 首次编译较慢；用依赖缓存和 sccache 后，增量编译加整条流水线通常 10 分钟内
- 每个产物生成 GitHub 构建证明，服务器安装前校验；部署账号只能执行固定安装脚本
- 服务器保留最近 5 个版本，一条命令回滚；数据库迁移随版本执行，破坏性变更拆成两次发布
- Renovate 每周提依赖升级 PR

**扩容（看真实数据，不提前加机器）**

| 指标（持续一周） | 动作 |
| --- | --- |
| 峰值 CPU > 70% 或内存 > 80% | 热备机分担只读查询 |
| 数据库 > 300 GB 或缓存命中率 < 99% | 数据库独立到专用机器 |
| 同时在线持续 > 3000 或 API 超过指标 | 增加 API 机器 |
| 帖子 > 2 亿 | 帖子表按 id 分区归档 |
| RPC 账单接近一台节点服务器租金 | 另租机器自建 Arbitrum 节点（还需要以太坊主网 RPC），按当时官方配置要求选型，第三方 RPC 改作备用 |

热备机（上线后加，4 核 8 GB）：PostgreSQL 流复制 + Valkey 副本，主机故障时切换 Cloudflare 回源，约 10 分钟恢复。

**论坛页面部署方式**：Next.js 跑在自有服务器。评估过 Cloudflare Workers（按请求计费，本项目流量估算每月约 50–400 美元，不划算）和把页面编进后端程序（需放弃 React 生态），均暂不采用。

## 14. 开发规范与前端设计

三条原则：只写论坛独有的业务代码，其余用成熟库；同一条规则只在一处定义，其他地方自动生成；不过质量门禁不能合并。

**禁止自己实现**

| 领域 | 必须使用 | 禁止 |
| --- | --- | --- |
| 密码学与签名 | webauthn-rs、alloy、viem | 自写验签、哈希、随机数 |
| 合约基础 | OpenZeppelin（SafeERC20、ReentrancyGuard、EIP712、SignatureChecker）+ Solady ERC-6492 | 自写转账、重入锁、验签；只用 ecrecover（智能账户签名会全部失败） |
| AA 钱包 | ZeroDev SDK + viem | 自己组装 UserOperation |
| HTML 过滤 | ammonia（后端）、DOMPurify（前端） | 正则过滤 |
| 任务队列 | apalis | 自写轮询表 |
| 限流 | Valkey 滑动窗口中间件 | 进程内计数器 |
| 金额 | alloy U256、viem parseUnits | 浮点数 |
| UI | shadcn（Radix）、react-hook-form + zod、TanStack Query | 从零写弹窗、表单状态、缓存 |

新增依赖前检查维护活跃度、下载量、许可证、已知漏洞，写进 PR 说明；优先用 tokio / tower 生态的成熟 crate；禁止 unsafe（依赖库除外）。

**单一事实来源（自动生成，不手抄）**

| 内容 | 唯一定义处 | 生成到 |
| --- | --- | --- |
| 合约接口 | Solidity 源码 | Rust：alloy sol! 宏；前端：wagmi CLI |
| 后端 API | Rust 类型 + utoipa | OpenAPI → openapi-typescript 前端类型与客户端 |
| 数据库 | sqlx 迁移 + 查询 | 编译期检查的 Rust 代码 |
| 链配置 | 链配置文件（单链 Arbitrum One） | 后端配置与前端常量（合约、USDT 地址与精度） |
| 错误码 | Rust 中的错误码定义 | OpenAPI 错误类型，前端显示中文提示 |
| 设计令牌 | Tailwind 主题 + CSS 变量 | 所有组件 |

手续费、gas 费、分期解锁在合约、Rust、TypeScript 三处都要算，用一份共享 JSON 测试向量同时驱动三边测试。

**编码约定**
